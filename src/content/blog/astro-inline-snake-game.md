游戏页最初只有一个空状态。那时我想得很简单：以后把 AI 小游戏放进来，像图库和文章一样慢慢积累。真的开始做第一件作品时，第一个问题却不是玩法，而是入口应该是什么样子。

如果点游戏卡片后进入新的详情页，再点一次“开始”，体验会像浏览内容，而不是玩游戏。这次的目标很明确：游戏卡片要像文章列表一样清楚，但点开后不能跳页，游戏就在当前页面启动。

## 卡片负责介绍，游戏留在原处

游戏页现在分成两层。第一层是可直接游玩的卡片，包含封面预览、标题、说明和标签；第二层是藏在卡片下方的游戏区域。点击卡片后，游戏区域展开，浏览器地址仍然停留在 `/games/`。

结构可以简化成下面这样：

```html
<article>
  <button aria-expanded="false" aria-controls="snake-player-panel">
    贪吃蛇 · 立即游玩
  </button>

  <section id="snake-player-panel" hidden>
    <canvas></canvas>
  </section>
</article>
```

这里的 `hidden` 不是视觉上的装饰。游戏未打开时，它确实不会显示，也不会进入页面布局；关闭游戏时重新加回 `hidden`，同时停止动画循环。按钮的 `aria-expanded` 则告诉辅助技术当前到底是展开还是收起。

这样既保留了“作品列表”的感觉，也避免了游戏详情页和游戏本体各占一个路由。以后增加第二、第三个小游戏时，只需要继续往列表里添加同样的条目。

## 用网格和固定步长控制节奏

贪吃蛇的画面由 Canvas 绘制，但移动并不依赖屏幕刷新率直接推进。棋盘固定为 24 列、18 行，每个格子都有明确坐标。蛇头和食物都只是网格里的点，判断碰撞时比较坐标即可。

真正的移动节奏由累计时间和当前速度共同决定：

```js
const stepDuration = getStepDuration();
stepAccumulator += elapsed;

if (stepAccumulator >= stepDuration) {
  stepAccumulator = 0;
  stepGame();
}
```

得分越高，每一步的间隔越短，但速度有一个下限。这样游戏会逐渐变快，又不会在连续吃到几个光点后突然快得无法操作。

第一版最容易出错的地方不是画蛇，而是方向。玩家在一帧内连续按下两个方向键时，如果直接覆盖当前方向，就可能绕过“不能立即反向”的检查。因此按键只写入下一步方向，真正执行移动时再把它设为当前方向。

碰撞判断也需要考虑尾巴。没有吃到食物时，蛇尾会同时移走，所以新蛇头进入旧尾巴所在格并不算撞到自己；吃到食物时不缩短尾巴，才需要检查完整身体。

## 键盘和触屏都要能玩

桌面端支持方向键和 WASD，空格或 `P` 暂停，`Esc` 收起游戏。手机端没有实体键盘，所以游戏旁增加了四个方向按钮，并在画布上提供滑动操作。

这次没有为两套设备写两份游戏逻辑。键盘、方向按钮和滑动最终都调用同一个改变方向的方法：

```js
function changeDirection(nextDirection) {
  const isReverse =
    nextDirection.x === -direction.x &&
    nextDirection.y === -direction.y;

  if (!isReverse) {
    queuedDirection = nextDirection;
  }
}
```

暂停和游戏结束共用同一层提示面板。游戏结束后显示本局分数；如果刷新最高分，再把结果写入本地存储。最高分只保存在当前浏览器里，不需要账号，也不会为了一个简单街机游戏先要求登录。

## 最后检查的是页面，而不只是构建

代码能够通过 Astro 构建，只能证明语法和资源路径没有问题。真正完成前，还需要在浏览器里实际点击卡片、用键盘改变方向、暂停、继续、撞墙结束和重新开始。

响应式检查也没有只看首页截图。390px 和 320px 宽度下分别确认了游戏画布、计分栏、方向按钮和页面整体都没有横向溢出。游戏在窄屏上会变成纵向布局，方向按钮会放大到适合手指点击的尺寸。

## 第一局只是一个开始

这次没有急着把“AI”加到玩法里。对游戏页来说，先跑通一件真正能玩的小作品，比先堆一组尚未完成的入口更重要。卡片、内嵌启动、统一输入和可重复测试的页面结构已经搭好，后面再接入需要模型判断、生成或实时交互的小游戏，也仍然可以复用这套外层体验。

现在点开渔情游戏页，第一局可以直接开始了。

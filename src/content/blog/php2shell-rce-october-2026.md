10 月 21 日，PHP 团队发布了紧急安全更新。这次不是某个 CMS 插件、模板或第三方库出了问题，而是 **PHP 核心运行时**中的两个漏洞，可以在满足条件时导致未认证远程代码执行（RCE）。

安全研究团队 Wiz 将其称为 **PHP2Shell**。这个名称容易让人联想到 Log4Shell，但它真正重要的地方不是名字，而是漏洞所在的层级：即使应用代码本身没有明显错误，只要运行在受影响的 PHP 环境中，攻击面依然存在。

截至本文发布时，官方补丁已经发布，CISA 也已把两个漏洞加入已知被利用漏洞目录。问题不再主要是“有没有补丁”，而是有多少存量系统还没有真正完成升级和重启。

## 事件概览

这次披露包含两个独立但可以组合利用的核心漏洞：

- **CVE-2026-109618**：内存耗尽（OOM）处理不当，导致请求内存处于无效状态。
- **CVE-2026-109619**：PHP 全局状态在请求结束后仍指向已释放内存，后续请求可能使用这些过期状态。

PHP 官方将两个问题都评为关键级别，并明确表示：**更新到包含完整补丁的版本是唯一可靠的修复方式。**

修复版本为：

- PHP 8.5.12
- PHP 8.4.27
- PHP 8.3.36
- PHP 8.2.35

PHP 8.1 及更早版本已经停止官方常规支持。PHP 团队为部分旧版本提供了最小源码补丁，但长期运行这些版本的系统仍应尽快规划升级。

## 起因：一个旧设计，踩中了新的利用方式

### 第一个问题：OOM 让请求在错误的时机退出

PHP 在某些内存耗尽场景中使用 `longjmp()` 跳回上层，以放弃当前上下文并终止请求。但在部分执行阶段，请求内存还没有完全初始化，或者刚被临时发布。

如果此时发生内存分配失败，流程可能在错误的位置提前退出，留下一个看起来仍然有效的内部状态。请求关闭阶段随后读取或判断这块状态，就可能造成内存破坏。

更危险的是，触发 OOM 的并不一定是一个“异常庞大”的请求。攻击者可能通过构造 multipart 表单、输入数量和其他请求结构，在看似正常的限制内不断逼近内存边界。GHSA-w8hw-w9fx-j79w 指出，在 Apache `mod_php` 的默认输入和内存限制下，研究人员通过普通 HTTP 请求验证了完整 RCE，而且攻击可以发生在应用代码开始执行之前。

### 第二个问题：上一个请求的内存，被下一个请求继续使用

PHP 的工作进程会长期存活。正常设计中，一个请求结束后，其响应、会话、错误对象和扩展状态都应被清理。

但某些致命错误可能中断清理流程，使工作进程的全局字段继续指向上一个请求拥有的内存。请求堆随后被释放，下一次请求却可能在正常初始化完成前读取这块“过期状态”。

这构成了典型的 **释放后使用（use-after-free）** 问题。攻击者需要同时找到：

1. 一个能留下危险状态的“生产者”。
2. 一个在后续请求初始化前读取该状态的“消费者”。

会话上传进度、错误处理、执行超时和某些配置路径都可能参与这个过程。攻击者通过反复请求和调整堆布局，最终可能把内存破坏转换成远程代码执行。

Wiz 的研究指出，这些底层问题存在时间很长；真正困难的是把多个缺陷串成稳定利用链。AI 模型在这次研究中降低了分析、适配不同内存布局和验证补丁的成本，但这并不改变根因：问题仍然来自 PHP 对请求生命周期和失败状态的管理。

## 经过：从协调披露到野外扫描

根据 PHP 官方时间线和研究团队说明，事件大致经历了以下几个阶段：

### 1. 漏洞发现与联合验证

Wiz Research 在对外披露前与 PHP 团队、安全厂商和云服务商合作，验证漏洞、测试补丁，并准备用户指南和临时缓解措施。

研究团队使用前沿模型辅助分析 PHP 代码、适配不同运行环境和调试利用链。这个细节值得关注：复杂漏洞的发现和利用正在变得更快，过去能够依靠“利用门槛很高”提供保护的系统，风险正在下降。

### 2. 10 月 20 日发布预告

PHP 团队提前发布公告，说明将在 10 月 21 日 14:00 UTC 发布一次包含两个关键漏洞修复的安全版本。这种短暂预告给基础设施提供商和发行版维护者留下了协调窗口。

### 3. 10 月 21 日紧急更新

PHP 发布 8.5.12、8.4.27、8.3.36 和 8.2.35，同时公开两个 GitHub Security Advisory。PHP 官方明确提醒：所有处理 Web 请求的 PHP 安装都应视为存在风险，包括 PHP-FPM、Apache `mod_php`、php-cgi、FrankenPHP 和 LiteSpeed。

其中 Apache `mod_php` 被认为是最高风险配置，因为研究团队展示了在请求启动阶段直接触发漏洞的路径。

### 4. 披露后出现自动化扫描与利用尝试

补丁发布后，Arctic Wolf Labs 观察到大量自动化请求开始探测 `session.upload_progress` 等功能。部分请求只是检查环境，部分则尝试写入会话数据、验证命令执行或下载第二阶段载荷。

这些流量证明攻击意图真实存在，但仅凭请求记录不能证明每次尝试都成功。对于仍未升级的系统，这不应被理解成“目前只是扫描”。

### 5. 10 月 26 日进入 CISA KEV

CISA 在 10 月 26 日将 CVE-2026-109618 和 CVE-2026-109619 加入已知被利用漏洞目录，要求相关联邦系统在 10 月 29 日前完成处置。是否与勒索软件活动有关，CISA 当前标注为“Unknown”。

## 结果：补丁已出，但风险没有自动消失

这次事件的直接结果是 PHP 官方已经修复底层问题，并提供了版本化更新。补丁修正了 OOM 的退出方式，也开始在请求边界重置更广泛的全局状态，避免请求拥有的内存继续跨请求存活。

影响面并不只取决于 PHP 版本：

- 直接暴露在公网的 PHP 应用风险最高。
- 使用 Apache `mod_php`、多个工作进程和默认上传配置的环境需要优先检查。
- PHP-FPM、php-cgi、FrankenPHP 和 LiteSpeed 也属于风险环境，只是不同路径的利用条件不同。
- 容器镜像、旧虚拟机、托管面板和第三方设备中可能藏着被遗忘的 PHP 运行时。
- 漏洞位于解释器层，WAF 和应用层输入校验不能替代系统更新。

Wiz 还展示了独立的内存信息泄露风险。即使攻击者暂时没有拿到代码执行，进程内存中也可能存在密码、令牌、API Key 和证书。

## 现在应该检查什么

### 1. 先确认真实版本和运行方式

检查服务器、容器镜像和构建产物中的 PHP 版本，而不是只看项目配置文件。还要确认使用的是 `mod_php`、PHP-FPM、php-cgi、FrankenPHP 还是 LiteSpeed，以及前端是否会向 PHP 传递特殊配置。

### 2. 升级后重启工作进程

更新软件包只是第一步。长时间运行的 FPM 子进程和容器实例必须滚动重启，否则旧进程仍可能继续处理请求。

### 3. 清理旧容器与基础镜像

基于旧 PHP 镜像构建的应用，即使源码没有变化，也需要重新构建。托管平台、CI 缓存和长期未部署的分支同样值得检查。

### 4. 临时缓解只能降低部分风险

如果确实无法立即升级，官方建议包括：

- 对 CVE-2026-109618，在管理配置中设置并强制执行 `memory_limit=-1`，同时限制请求体积和 multipart 复杂度。
- 对 CVE-2026-109619，关闭 `session.upload_progress.enabled`，并重启所有工作进程。
- PHP 8.5 环境可额外关闭 `fatal_error_backtraces`。

这些措施只能切断部分已知路径，不是完整修复。修改配置后如果没有重启全部 worker，也不会真正生效。

### 5. 开始检查异常请求和崩溃

可以重点查看：

- 异常 multipart 请求之后出现的内存限制错误。
- 集中的 HTTP 500 和 PHP worker 反复退出。
- 来源不明的超大或畸形 `PHPSESSID` 响应 Cookie。
- 访问 `session.upload_progress` 相关参数的自动化扫描。
- Web 服务日志中无法对应到正常业务请求的可疑载荷。

日志中没有异常，不代表系统没有被尝试攻击；攻击可能发生在应用日志记录之前。

## 这件事真正提醒了什么

PHP2Shell 最值得记住的，不是又出现了一个“年度最危险漏洞”，而是一个更结构性的变化：

**当 AI 降低了复杂漏洞的发现和利用成本，运行时、基础镜像和默认配置会重新成为安全边界。**

应用代码、依赖扫描和 WAF 仍然重要，但它们不能替代对语言运行时本身的管理。对于团队来说，最实际的动作不是制造恐慌，而是把 PHP 版本、进程模型、容器镜像和更新时间真正纳入资产清单。

补丁已经发布。接下来决定风险大小的，是升级覆盖率，而不是漏洞新闻传播得有多广。

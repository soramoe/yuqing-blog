上一轮优化把网站构建产物从约 39 MB 降到了 9.37 MB，但其中大部分仍然是图片。

这些图片虽然已经被压缩成 WebP，仍然需要跟着 Git 仓库进入 Cloudflare Pages 构建。原图留在仓库里，构建时还会复制一份优化图；图片越多，克隆仓库和上传静态资源的时间就越长。

所以这次的目标很明确：网站继续由 Pages 托管，图片改成由 Cloudflare R2 独立提供，页面只保留图片清单和远程 URL。

## 为什么不继续把图片放在 public

Astro 会把 `public/` 里的文件原样复制进构建产物。把图库放在 `public/gallery/` 最直接，但也会带来几个问题：

- 原始高清图会进入 Git 历史。
- 每次构建都要复制全部图片。
- Pages 部署包会跟着图片数量增长。
- 图片更新和页面发布绑在一起，无法单独处理。

更合理的做法是把媒体看作独立资源。网站只负责引用，媒体负责存储和分发。

## 最终结构

迁移后，数据流变成这样：

```text
本地原始图片
  ↓ Sharp 压缩
R2：yuqing-media
  ↓ 自定义域名
https://media.xhz6.com/gallery/...
  ↓
Astro 只保存文件名和图片尺寸
```

公开 Bucket 里只放压缩后的 WebP，不放原始文件。文章和图库仍然使用同一个图片 helper 生成响应式地址，只是根域名从网站自身改成了 `media.xhz6.com`。

## 创建 R2 Bucket 和自定义域名

在 Cloudflare R2 中创建了名为 `yuqing-media` 的 Bucket，然后为它绑定 `media.xhz6.com`。

绑定自定义域时，Cloudflare 自动预览了需要的 DNS 记录：

```text
类型：CNAME
名称：media
目标：yuqing-media
```

因为 `xhz6.com` 本来就在 Cloudflare 托管，这一步只需要确认连接域，DNS 和后续的 HTTPS 会自动处理。

生产环境没有使用临时 `r2.dev` 地址。那个地址适合测试，但正式站点更适合使用自己的域名，缓存、日志和安全策略也更清晰。

## 上传什么，不上传什么

这次一共上传了 57 个 WebP：

- 14 张图库图片，每张生成 480、960、1920 三档，共 42 个文件。
- 5 张封面图片，每张生成 480、960、1440 三档，共 15 个文件。

原始 PNG 和 JPG 没有放进公开 Bucket。

上传后没有只看控制台里的数量，而是用脚本逐一请求 57 个公开链接，确认全部返回 `200`。这个检查很重要，因为列表里显示对象存在，和浏览器能正确加载并不是同一个问题。

## 让 Astro 不再依赖本地文件夹

原来图库页面会在构建时读取 `assets/gallery/`，首页也读取同一个目录。图片被移走后，这种实现会直接让构建失败。

现在改成提交一份小型清单：

```json
[
  {
    "file": "20261027_043757_c4eb2d2aae11_1.png",
    "width": 1698,
    "height": 926
  }
]
```

清单放在 `src/data/gallery.json`，只保存文件名和尺寸。图库标题、排序和日期仍然由代码推导。

图片地址生成逻辑也只改了一处：

```ts
const mediaBaseUrl = "https://media.xhz6.com";
const variants = widths.map(
  (width) => `${mediaBaseUrl}/${pathWithoutExtension}-${width}.webp`,
);
```

这样首页、图库和文章封面都会自动使用 R2，不需要在每个页面手写远程链接。

## 图片优化从构建流程里拆出去

之前每次执行 `pnpm build` 都会先运行 Sharp，压缩全部图片。

但 Cloudflare Pages 的构建环境里现在没有图片来源，也没有必要在每次写文章时重新生成媒体。因此移除了 `prebuild` 阶段的图片处理，构建只负责 Astro 和 Pagefind。

本地新增图片的工作流改为：

1. 把原图放进不参与 Git 的 `media-src/`。
2. 执行 `pnpm optimize:images`。
3. 把生成的 WebP 从 `media-upload/` 上传到 R2。
4. 提交更新后的图片清单和页面代码。

`media-src/` 和 `media-upload/` 都被 `.gitignore` 排除。原始图片仍然在电脑上保留了一份备份，但它们不会进入网站仓库、Pages 构建或正式部署包。

## 旧图片路径怎么处理

图片从仓库删除后，历史 URL 不能一直悬空。

例如原来的原始图路径是：

```text
/gallery/某张图片.png
```

迁移后图片的真实位置已经是：

```text
https://media.xhz6.com/gallery/某张图片-1920.webp
```

为了避免旧收藏、搜索结果或外部引用返回原图，在 Pages 中添加了旧路径重定向：

```text
/gallery/:file /gallery/ 302
/covers/:file /gallery/ 302
/media/optimized/:section/:file /gallery/ 302
```

这里使用参数匹配具体的旧文件名，而不是直接写 `/gallery/*`。后者会连 `/gallery/` 首页本身也一起匹配，导致首页反复重定向到自己。使用临时重定向而不是永久重定向，则是因为迁移刚完成时还可能继续调整最终地址；先用 302 把旧请求收回正常页面，比长期承诺一个临时目标更稳妥。

另外，Cloudflare 之前缓存过一部分旧图片。即使代码已经删除了文件，缓存仍可能在短时间里返回旧的 200 响应。

处理方式是先让全站缓存失效，再对旧图库和旧封面的精确 URL 做一次清理。清理完成后，旧图片路径返回 `302`，新 R2 图片继续返回 `200`。

这说明“从仓库删除图片”和“公网不再提供旧图片”并不是同一个步骤。静态资源迁移必须把缓存也纳入检查。

## 迁移后的结果

最终验证结果如下：

- 57 个 R2 图片链接全部返回 `200`。
- 首页和文章页的图片 URL 都指向 `media.xhz6.com`。
- `public/` 和 `dist/` 中不再包含 PNG、JPG 或 WebP。
- 构建产物从约 9.37 MB 降到约 0.96 MB。
- Pages 构建只花二十多秒，仓库克隆从分钟级回到一两秒。
- 旧图片路径会跳到图库，不再返回原始大图。

页面加载时，浏览器先拿到轻量的 HTML，再从 R2 并行请求适合当前屏幕的 WebP。媒体有自己的域名和缓存策略，网站也终于不再背着几十 MB 图片部署。

## 这次学到的几件事

R2 不是“把文件扔上去就结束”。它需要一份稳定的对象命名规则，也需要页面知道如何根据尺寸拼出地址。

原始文件不适合直接公开。公开 Bucket 只放最终 WebP，高清源图留在私有空间或本地备份，既能防止大文件被随意下载，也方便以后重新生成不同尺寸。

内容迁移必须同时考虑缓存。代码发布成功了，不代表旧 URL 立刻消失；反过来，旧 URL 还在，也不代表新页面没有用上 R2。最终要把页面源码、真实请求、响应头和对象存储一起验证。

对一个内容不多的静态博客来说，这套结构已经够用：页面是轻量的，媒体是可替换的，发布流程只更新 HTML 和清单。以后图片继续增加，也不会再把整个网站的构建拖回几十 MB。

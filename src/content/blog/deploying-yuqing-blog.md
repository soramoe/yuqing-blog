今天做了一件筹备了一段时间的事：把渔情从本地预览变成了一个真正可以通过互联网访问的网站。

正式地址是 [xhz6.com](https://xhz6.com)。它现在还是一个很安静、内容不多的博客，但至少从“想做一个地方”走到了“这里真的存在”。

这次部署没有采用服务器加数据库的传统方式，而是使用静态生成：Astro 负责构建页面，GitHub 保存源码，Cloudflare Pages 负责自动构建和全球分发，域名直接指向最终站点。

## 先把构建变可靠

部署之前最重要的一步不是配置平台，而是确保项目能够稳定构建。

```bash
pnpm build
```

构建结果位于 `dist/`，其中包含首页、博客列表、文章详情、标签页、搜索页、RSS 和 sitemap。只要本地构建失败，就不应该继续配置线上环境，否则平台上的报错只会更难定位。

这一次还顺手确认了几个容易被忽略的点：

- 所有文章地址都要能直接打开，而不是只能从列表跳转。
- RSS 和 sitemap 必须使用正式域名。
- 图片和 CSS 不能被错误地写成只适用于本地开发的路径。
- 搜索索引需要在静态页面生成完成后再创建。

## 让代码先到 GitHub

项目在本地完成提交后，需要推送到 GitHub 仓库。这个环境里直接访问 Git 的 GitHub HTTPS 地址会连接重置，但网页可以正常访问，说明问题出在终端使用的网络通道，而不是仓库本身。

最后的解决方式是使用 GitHub 支持的 SSH 443 通道，并为这个仓库单独创建部署密钥。密钥只添加到 `yuqing-blog` 这一个仓库，私钥保存在本机，不写进代码，也不放进文章。

远程地址大致如下：

```bash
git remote set-url origin ssh://git@ssh.github.com:443/OWNER/REPO.git
```

这样做比把账号密码写进脚本更安全，也比扩大整个账号的访问权限更克制。部署基础设施也应该遵守最小权限原则。

## 连接 Cloudflare Pages

Cloudflare 现在的控制台把 Workers 和 Pages 放在了一起。创建站点时，可以选择直接上传静态文件，也可以连接 GitHub 仓库。为了以后写完文章只需要推送代码，最终采用了 Git 集成。

第一次安装 GitHub 应用后，Cloudflare 的回跳状态出现错误。按照页面提示完全卸载应用，再重新安装，并只授权 `soramoe/yuqing-blog` 一个仓库，连接才恢复正常。

最终构建配置是：

```text
Framework preset: Astro
Build command:     pnpm build
Output directory:  dist
Node version:      24
```

这里没有服务器常驻进程。Cloudflare 在每次推送 `main` 分支后拉取代码、安装依赖、执行构建，然后把 `dist/` 发布到它的边缘网络。

## 把根域名接上

站点一开始可以先用 `pages.dev` 提供的临时地址访问，但真正上线还是要绑定自己的域名。

切换根域名之前，先检查了 DNS 中是否已经存在正在使用的网站记录。确认根域名没有旧的 A 或 CNAME 后，才在 Pages 的自定义域功能中加入 `xhz6.com`。Cloudflare 自动创建了指向 Pages 项目的根域名记录，并完成 HTTPS 证书。

如果域名托管在其他服务商，逻辑也类似：按照平台给出的目标创建 CNAME；根域名不支持 CNAME 时，需要使用服务商提供的 ALIAS 或 CNAME 展平能力。

域名生效后，站点的 Canonical、RSS 和 sitemap 地址也全部从临时域名切换成了正式域名。

## 上线检查不是只打开首页

部署成功不等于完成。最后做了一轮最简单的检查：

1. 首页和博客列表返回正常状态码。
2. HTTPS 证书已经生效。
3. 文章详情可以直接访问。
4. RSS 和 sitemap 返回正确内容。
5. 移动端布局没有横向溢出。
6. 明暗主题和静态搜索可以正常使用。
7. 推送新的提交后，Cloudflare 能再次自动部署。

这些问题看起来零碎，但比“我这边能打开”可靠得多。

## 这次留下的经验

最大的感受是：部署不是把文件扔到一个地方，而是让构建、版本管理、权限和域名组成一条可以重复执行的路径。

一次手工上传可以解决今天的问题，但自动构建才能解决以后的问题。部署密钥、GitHub 应用和域名记录都尽量收窄权限，也能让以后排查问题时知道每一层负责什么。

渔情现在已经有了一个正式地址。接下来要做的不是继续堆配置，而是慢慢把真正想写的内容放进来。

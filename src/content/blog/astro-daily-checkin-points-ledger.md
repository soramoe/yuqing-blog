登录和评论做完之后，用户系统还缺一个能持续积累的东西。评论适合表达，签到适合形成习惯，而积分可以把这些行为记下来。

这次先做最简单的闭环：每天签到一次，获得 5 积分；账户页可以看到余额，积分中心可以看到签到状态和最近流水。没有充值，也没有兑换，先把“积分不会重复发、余额不会算错”解决好。

## 不直接存一个 balance

只给用户保存一个积分数字看起来最简单：

```text
用户 A：35 分
```

但很快就会遇到问题：这 35 分是哪来的？某次奖励有没有发过？删除一条流水后余额怎么对账？

因此这次拆成三张表：

- `point_account`：保存当前余额，读取个人中心时不需要每次重算。
- `daily_checkin`：记录每天的签到。
- `point_transaction`：记录每一笔积分变化，是后续对账的依据。

余额负责速度，流水负责事实。两者一起更新，才能既快又不出错。

## 用唯一约束防止一天签到两次

签到表里保存用户、签到日期和当天获得的积分，并对“用户 + 日期”建立唯一索引：

```sql
CREATE UNIQUE INDEX daily_checkin_user_date_unique
ON daily_checkin (user_id, checkin_date);
```

前端按钮可以禁用，但前端永远不是最后一道防线。即使用户同时打开两个页面，或者直接请求签到接口，数据库也只能接受同一天的一条签到记录。

日期统一按北京时间计算。用户在中国时间凌晨 0 点以后就算进入新的一天，不会因为服务器使用 UTC 而把签到日期错开。

## 一次签到写了四步

真正签到成功时，需要同时完成：

1. 确保用户已有积分账户。
2. 写入当天的签到记录。
3. 给账户余额增加 5 分。
4. 写入一条 +5 的积分流水，并记录变化后的余额。

这四个操作放进 Cloudflare D1 的同一个 batch。只要其中一步失败，整组写入不会留下“签到成功但积分没加”或者“积分加了但没有流水”的半成品。

流水中的 `balance_after` 使用更新后的账户余额生成：

```sql
INSERT INTO point_transaction (
  id, user_id, amount, type, description,
  reference_id, balance_after, created_at
)
VALUES (
  ?, ?, 5, 'checkin', '每日签到', ?,
  (SELECT balance FROM point_account WHERE user_id = ?),
  ?
);
```

服务端固定发放 5 分，客户端不能提交奖励数量。用户只能请求“我要签到”，不能请求“给我加多少分”。

## 连续签到天数怎么算

余额和流水解决“有多少分”，连续天数解决“坚持了多久”。

系统读取用户最近 366 条签到日期，从今天开始向前数。如果今天还没签到，就从前一天开始判断；中间少一天，连续记录就归零。

这不需要额外维护一个容易算错的 streak 字段。签到记录本身就是事实来源，展示时再计算，历史数据改了以后结果也会立即正确。

目前连续签到只做展示，没有额外阶梯奖励。以后如果增加“连续 7 天多送积分”，应该再生成一条独立流水，而不是直接修改旧余额。

## API 和页面怎么配合

积分中心使用两个接口：

```text
GET  /api/points
POST /api/points/check-in
```

读取接口同时返回余额、累计获得、连续天数、今天是否已签到和最近 12 条流水。签到接口完成事务后返回最新摘要，页面立即刷新数字，不需要再猜当前状态。

前端会先读取 Better Auth Session。未登录访问积分接口返回 `401`，没有用户 ID 就不能创建签到记录。

账户页增加了积分中心入口。积分页本身只缓存 HTML 外壳，真正的数据通过禁止缓存的 API 获取。账户、登录、积分和审核页面也统一设置了 `Cache-Control: no-store`，避免部署新页面后被旧静态缓存挡住。

## 上线后的实际验证

第一次正式签到后，实际结果是：

```text
当前余额：5
累计获得：5
连续签到：1 天
签到流水：+5，余额 5
```

数据库中的账户余额、签到日期和流水金额完全一致。刷新积分页后，签到按钮变成“今日已签到”并禁用；未登录读取积分接口则返回 `401`。

这比页面显示一个数字更重要的是三处数据能够互相解释：

- 余额说明现在有多少分。
- 签到记录说明为什么获得。
- 流水说明每一次变化和变化后的余额。

## 这次没有做什么

目前积分只能通过签到获得，还不能评论奖励、消费或兑换，也没有充值入口。

充值涉及支付、退款、风控和合规，不适合和签到一起仓促上线。下一阶段可以先让优质评论获得积分，再设计积分能兑换什么。无论增加哪种来源，都应该继续遵守同一条规则：

> 先写流水，再改余额，所有奖励都由服务端决定。

这样一来，以后功能越来越多，积分系统仍然能解释清楚每一分的来路和去向。
